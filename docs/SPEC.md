# SuperMeeting — 仕様・アイデア置き場（SPEC）

壁打ち（仕様検討）の成果を貯めるための**生きたドキュメント**です。
Chat で発散したアイデアや決めたことを、ここに書き出しておくと、
以降どの Claude Code セッションからも参照できます（会話は揮発、ファイルは永続）。

> - **恒久的な前提・アーキテクチャ**は `CLAUDE.md` を参照（重複させない）。
> - このファイルは「**何を作るか / なぜそう決めたか / これから何を検討するか**」を扱う。
> - 迷ったら追記優先。決まったら「決定ログ」へ、実装したら「現在の仕様」へ移す。

---

## 使い方（運用ルール）

1. 思いついたアイデアは **§バックログ** に1行足す（粗くてOK）。
2. 検討して方針が決まったら **§決定ログ** に「決定・理由・日付」を書く。
3. 実装が済んだら **§現在の仕様** に反映し、バックログから消す。
4. 判断に迷う点は **§未解決の論点** に置いて、壁打ちの起点にする。

---

## プロダクト概要 / ゴール

Google Meet などのオンライン会議で、**リアルタイムに議事ノートを画面共有してファシリテーション**する。
音声を書き起こし、AI が「要約 / 論点 / 決定事項 / TODO / 未解決の問い / 図示 / 調査・社内情報検索」に整理する。

- 想定ユーザー: 会議のファシリテーター
- 使い方の前提: ファシリが本アプリを画面共有しながら進行
- 提供価値: 議論の可視化・抜け漏れ防止・意思決定と宿題の明確化

## 現在の仕様（実装済み）

| 機能 | 現在の挙動 |
|---|---|
| 書き起こし | ブラウザ標準の Web Speech API（ja-JP / en-US 切替、自動再開）。手入力・サンプル投入も可 |
| 話者分離 | Chrome 拡張が Meet の発言者を検出し話者付与（自動＋手動固定）。拡張なしでも話者バーで手動切替 |
| 議事整理 | 現在の議論の要約 |
| 論点 | ステータス（未着手/議論中/結論あり）付きで一覧 |
| 決定事項 / TODO | 決定事項の抽出、TODO は担当者を可能な範囲で自動付与 |
| 図示 | Mermaid flowchart で議論構造を描画 |
| 調査 | Claude の web_search による Web 調査（要 APIキー、未設定はモック）。結果は調査フィードに ResearchCard として新着順に積まれる（上限 20 枚、古いカードは折りたたみ） |
| 社内情報検索 | プロバイダ抽象 + Slack コネクタ実装済み（`SLACK_USER_TOKEN` で有効化、未設定時はモック）。search.messages ＋ public チャンネル限定フィルタ（`SLACK_INCLUDE_PRIVATE=1` で解除可）、メッセージ内 URL を最大 2 件サブソース展開。Web と束ねず独立カードとして非同期到着（/api/research の target で片方のみ実行） |
| 自動リサーチ | 発話確定ごとに Haiku（`ANTHROPIC_TRIGGER_MODEL`、既定 `claude-haiku-4-5`）が検索要否を判定（`/api/trigger`）し、web/internal のカードを自動で積む。ガード 3 枚（in-flight バッファによる実質 2〜3 秒間隔の判定 / 実行済みクエリの正規化キャッシュによる重複抑制 / 3 並列上限・超過時は最古の実行中カードを Abort）。トグルは既定 OFF（発話が外部の Web 検索に送られるため明示 ON）。`ANTHROPIC_API_KEY` 未設定時は常に shouldSearch=false |
| エンジン | APIキーがあれば Claude、無ければルールベース/モックに自動フォールバック |

## 検討中の大型機能: 自動リアルタイムリサーチ（設計）

> 2026-07-05 の壁打ちで方針決定。§決定ログの同日付エントリが意思決定の記録、本節がその設計詳細。
> 実装はフェーズ①→②→③の順に段階導入する（各フェーズで単体検証可能）。

### ゴール / 体験

会議中の発言に反応して、**社内（Slack）と Web の関連情報を自動検索し、カードとしてリアルタイム表示**する。

- 体験目標レイテンシ: **Slack 結果は発話確定から 2〜3 秒**、Web 結果は 5〜20 秒で遅れて滑り込む
- 最大のリスクは「アテンション汚染」（画面共有中のボードに的外れな結果が流れると価値が毀損）。
  まず垂れ流しで検索品質を磨き、その後に関連性フィルタ・紐づけ可視化へ進む

### アーキテクチャ（高速トリガーレーン）

```
発話確定 (useTranscription onFinal)
  → 判定キューへ投入（in-flight 中の発話はバッファし次回まとめて判定）
  → POST /api/trigger （Haiku, structured output）      … 0.5〜1 秒
  → 検索タスク確定 → web / internal を「別々のカード」として並列実行
       internal (Slack): 0.5〜1 秒 → 発話から 2〜3 秒でカード表示
       web (Claude web_search): 5〜20 秒 → 遅れて到着
```

- 既存の 15 秒周期の分析ループ（`useAnalysis`）とは**独立**した高速レーン
- `runResearch` の web＋internal 待ち合わせは**解体**し、origin ごとに独立したカードとして非同期表示する
  （最速の Slack が最遅の Web 検索に引きずられるのを防ぐ）

### /api/trigger の入出力

入力: 直近 6〜10 発話のスライディングウィンドウ、最新分析の topics 要約（あれば）、直近の実行済みクエリ一覧

出力スキーマ（structured output）:

```typescript
{
  shouldSearch: boolean,
  tasks: [{
    intent: string,        // 何を明らかにしたいか（Web 検索用の自然文）
    slackKeywords: string, // Slack 検索用の短いキーワード列（2〜4語。in:/after: 修飾子可）
    target: "web" | "internal" | "both",
    triggeredBy: string,   // 発端となった発言の引用
  }]
}
```

- モデルは Haiku（環境変数で差し替え可、既定 `claude-haiku-4-5`）。判定は毎発話ごとに走らせてよい
- **クエリの二本立てが検索品質の最大のレバー**: Web 用は自然文、Slack 用はキーワード列
  （Slack 検索はキーワードマッチのため、自然文をそのまま投げても当たらない）

### 暴発防止のガード（3枚）

1. 判定の最小間隔（実質 2〜3 秒に 1 回。in-flight 中に確定した発話はバッファ）
2. 実行済みクエリの正規化キャッシュ ＋ プロンプトへの「調査済み一覧」注入で重複検索を抑制
3. 検索の同時実行上限（2〜3 並列）。超過分は古い順に AbortController でキャンセル

### データモデル（カード）

```typescript
ResearchCard {
  id, query, slackKeywords?, target,
  status: "queued" | "searching" | "done" | "error",
  trigger: "auto" | "manual",
  triggeredBy?: { segmentId, quote },  // ★表示しなくても最初から保持（後の可視化と品質デバッグに必須）
  at, summary?, sources[]
}
```

### UI: AutoResearchPanel（右端フィード）

- 新着が上に積まれるフィード。表示上限 20 枚、古いものは自動折りたたみ
- 自動/手動をバッジで区別。手動調査もカードとして同じフィードに流す
- `triggeredBy` の引用は開発中は小さいグレー文字で表示（検索品質デバッグ用）
- 紐づけ可視化（発言⇔カードのハイライト等）は品質が磨けた後のフェーズ

### Slack コネクタ（最初の実コネクタ）

- API: `search.messages` ＋ ユーザートークン xoxp（`SLACK_USER_TOKEN`、スコープ `search:read`）
  - 検索系スコープは**ユーザートークンのみ対応**（bot トークン xoxb では呼べない）
  - 社内アプリなら OAuth フロー不要。アプリ設定画面の User Token Scopes に `search:read` を追加 →「Install to Workspace」でトークン即発行
- **public チャンネル限定フィルタ（必須）**: 個人トークンの検索結果には DM・プライベートチャンネルが混ざる。
  画面共有中のボードに DM 断片が出る事故を防ぐため、レスポンスの各マッチのチャンネル情報で
  `is_private / is_im / is_mpim` を除外（既定 public-only、設定で切替可。外部共有チャンネル `is_ext_shared` の除外もオプション検討）
- メッセージ本文から URL を抽出し、カード内にサブリンクとして展開
  （Slack メッセージに貼られた Confluence 等が本命の一次情報であることが多い）
- レートリミット注意: `search.messages` は Tier 2（20 リクエスト/分程度）。
  自動トリガーと組み合わせる際はクエリキャッシュ＋同時実行上限で流量を抑える
- 将来: Slack はレガシー `search:read` から Real-time Search API への移行を推奨している。
  bot トークンでの RTS はイベント由来の action_token が必要でスタンドアロン Web アプリとは相性が悪いため、
  MVP はレガシー API で割り切り、Slack アプリ化のタイミングで RTS 移行を再検討

### 段階導入プラン

| フェーズ | 内容 | 検証方法 |
|---|---|---|
| ①✅ | `runResearch` 束ね解体 ＋ フィードパネル基盤（2026-07-05 済） | 既存の手動調査で web/internal カードが個別・非同期に出る |
| ②✅ | `SlackKnowledgeSource` 実装（2026-07-05 済） | 手動調査で実 Slack ヒットが出る（public-only）。フィルタは `src/lib/research/slack.filter.test.ts`（`node --test`）で担保 |
| ③✅ | 高速トリガーレーン（/api/trigger ＋ ガード）（2026-07-06 済） | 発話から数秒で自動カードが出る。重複暴発しない。トグル OFF では /api/trigger への fetch が発生しない |

## 用語

- **エンジン**: 分析を生成する主体。`claude`（AI）/ `heuristic`（ルールベース）/ `mock`（調査のダミー）
- **話者ラベル**: 発話に付く発言者名。AI へは「話者名: 発言」形式で渡す
- **トリガーレーン**: 発話確定ごとに検索要否を高速判定する処理系（`/api/trigger`）。15 秒周期の分析ループとは独立
- **カード**: 自動/手動リサーチの結果 1 件の表示単位。origin（web/internal）ごとに独立して非同期に到着する
